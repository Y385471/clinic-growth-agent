# Clinic Growth Agent — Technical Spec

## How This Works, In Plain Language
The app is a website that lives on the internet (**Vercel**), so it keeps working when the owner's computer is off.

**Once a day, the alarm fires.** Vercel's **Cron** is a daily alarm. It wakes the agent, and the agent:
- collects the day's ads, chats, comments and reactions (in **practice mode**, a realistic made-up day; in **live mode**, the clinic's Facebook page);
- removes names and phone numbers before any text leaves;
- asks **Gemini**, Google's AI, to read the chats. Gemini says who booked, why others didn't, and what to try;
- saves everything in one connected record per person in **Supabase**, the online database the clinic's ERP already uses.

**The pages people use:**
- **The receptionist** opens a link on her phone and taps who came today.
- **The owner** opens the site and sees the funnel. Each stage shows its problem and fix. Tapping a stage opens its full dashboard. Everything is read from the same connected records, so nothing is fragmented.

**Learning:** every finding is saved as a **hypothesis** with a test. Each daily run re-checks the open hypotheses against the new data and marks them confirmed or rejected, with the evidence.

**Why this shape:** everything is free with no card, nothing needs to be installed on the owner's machine, and the whole app is plain web pages plus a few small server functions. There is no heavy framework to learn.

## The Core Journey Through the System
PRD ref: `prd.md > The Core Journey`.

1. **Morning.** The Vercel Cron calls `/api/run-daily`.
2. **Collect.** `lib/source.js` returns the day's ads, conversations, comments and reactions: generated by `lib/practice.js` in practice mode, or read from the Meta Graph API in live mode.
3. **Scrub.** `lib/scrub.js` replaces names and phone numbers with placeholders, keeping a private map so people stay linked.
4. **Analyse.** `lib/analyse.js` sends each conversation to Gemini. It gets back structured JSON: booked yes/no, booking date, loss reason, quote, sentiment and fear signals.
5. **Store.** The people, conversations, bookings and ads are saved to Supabase, and each person is linked to their ad and conversation.
6. **Learn.** `lib/learn.js` re-checks open hypotheses against today's numbers, updates their status, and asks Gemini for at most one new hypothesis per leaking stage.
7. **Evening.** The receptionist opens `/attend.html`. The page calls `/api/attendance` to list today's bookings, and each tap posts "attended".
8. **Next run.** If yesterday's attendance was never ticked, `run-daily` raises an alert for the owner.
9. **The owner** opens `/` (funnel), which calls `/api/funnel`. Tapping a stage opens `/stage.html?s=booking`, which calls `/api/stage?s=booking`.

## Stack
- **Plain HTML, CSS and JavaScript** for the pages. There is no framework and no build step, so the learner can read every file.
- **Vercel Functions (Node.js 24)**, one file per endpoint under `api/`. They use `"type": "module"` and named `GET`/`POST` exports; a default-exported handler hangs, a lesson from an earlier project. Docs: https://vercel.com/docs/functions
- **Vercel Cron Jobs** for the daily run, declared in `vercel.json`. Hobby-plan crons run once a day. Docs: https://vercel.com/docs/cron-jobs
- **Supabase (Postgres)**, reached with plain `fetch` over its REST API, so there are **zero npm dependencies**. Docs: https://supabase.com/docs/guides/api
- **Gemini API, free tier**, via plain `fetch` with JSON-schema output. Docs: https://ai.google.dev/gemini-api/docs
  - *Unverified: the current free model name and its daily request limit. Check both in the first build slice.*
- **Meta Graph API** for live mode: page conversations, comments, reactions and ads insights. Docs: https://developers.facebook.com/docs/graph-api
  - Live mode is built but not required for the demo.

## Where It Runs and How Someone Tries It
- **Deployed on Vercel** from the public GitHub repo, using Vercel's GitHub import in the browser. The Vercel CLI isn't available on this machine.
- **Environment variables** are set in Vercel only, never committed:
  - `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `GEMINI_API_KEY`
  - `MODE=practice|live`
  - live only: `META_PAGE_ID`, `META_PAGE_TOKEN`, `META_AD_ACCOUNT`
  - `CRON_SECRET`, which protects `/api/run-daily`
- **To try it:** open the Vercel URL. `/` is the owner view and `/attend.html` is the receptionist view.
- **The demo recording** runs in practice mode:
  1. Trigger day 1 (`/api/run-daily?day=1`, secret-protected).
  2. Show the funnel and a stage dashboard.
  3. Tick attendance.
  4. Trigger day 2 and show a hypothesis changing status and the advice updating.
- Required for submission: the demo video (1–3 min, uploaded to Vimeo) and the public GitHub repo containing `devpost/scope.md`, `prd.md` and `spec.md`.

## Look and Feel
- **Modern and light.** White and very light grey surfaces, one confident accent colour (teal/blue) for actions, and red/amber only to flag a leaking stage.
- **Clean sans-serif type** (Inter) with generous spacing, like a calm report rather than a dense trading screen.
- **Copy tone:** a smart team member reporting, in plain language with one next action per stage. The owner-facing text is in Arabic, right to left; practice conversations are in Egyptian Arabic.

## Components

### Daily Runner (`api/run-daily.js`)
Orchestrates one day: collect, scrub, analyse, store, learn, attendance check. It is idempotent per day, so a re-run replaces that day's results.
PRD ref: `prd.md > Daily automatic run`, `prd.md > States and Boundaries`.

### Data Source (`lib/source.js`, `lib/practice.js`, `lib/meta.js`)
It gives the runner the same shape of data in both modes.
- Practice mode generates a seeded, realistic clinic day with ads, conversations, comments and reactions. Day 2 reflects a fix applied, for example faster replies to price questions.
- Live mode reads the page through the Graph API.
PRD ref: `prd.md > Daily automatic run`.

### Privacy Scrubber (`lib/scrub.js`)
It replaces names and Egyptian phone numbers with placeholders before any text goes to Gemini, and keeps the mapping in Supabase only.
PRD ref: `prd.md > States and Boundaries` (Privacy).

### Conversation Analyst (`lib/analyse.js`)
This is the Gemini call with a JSON schema. Per conversation it returns `booked`, `booking_date`, `loss_reason` (from a fixed list plus free text), a short quote, and psychological signals (price anxiety, fear, trust, comparison).
PRD ref: `prd.md > Booking detection`, `prd.md > Stage problem and fix`.

### Hypothesis Engine (`lib/learn.js`)
Each hypothesis is a rule the code can check, for example "price-asking chats answered after 60 min book less than 20 %". It stores a threshold and the metric to recompute. Each run recomputes the metric and sets the status to testing, confirmed or rejected, with evidence. New hypotheses are proposed by Gemini, but they are **verified by code, not by Gemini**.
PRD ref: `prd.md > Hypotheses and learning`.

### Funnel & Stage API (`api/funnel.js`, `api/stage.js`)
It computes the stage counts from the connected records: ad → message → booked → attended. It returns the problem and fix per stage, the biggest leak, and, per stage, the linked ads, people, ranked reasons with quotes, and the active hypothesis. It also returns "lost people" for the latest drop.
PRD ref: `prd.md > Connected funnel and people`, `prd.md > Stage problem and fix`.

### Attendance (`api/attendance.js`, `public/attend.html`)
`GET` lists today's bookings; `POST` marks a person as attended. If the previous day was never ticked, the runner stores an alert.
PRD ref: `prd.md > One-tap attendance`, `prd.md > States and Boundaries`.

### Owner Screens (`public/index.html`, `public/stage.html`, `public/app.css`, `public/app.js`)
- The funnel home: stage cards showing count, problem and fix; the leak highlighted; the alert banner; "last updated"; and "What I've learned".
- The stage dashboard, linked to neighbouring stages.
PRD ref: `prd.md > Screens and Layout`.

## Data Model
All data lives in Supabase and persists between visits.
- `ads(id, day, name, spend, reach, clicks)`
- `people(id, alias, real_name_enc, phone_enc, first_seen_day, ad_id)`: the alias is what Gemini and the video see.
- `conversations(id, person_id, day, source[message|comment], text_scrubbed, first_reply_minutes, analysis jsonb)`
- `reactions(day, post_id, type, count)`
- `bookings(id, person_id, conversation_id, booking_date, attended bool null)`: `null` means not ticked yet.
- `hypotheses(id, stage, statement, metric, threshold, status, evidence jsonb, created_day, updated_day)`
- `runs(day, mode, status, alert text)`: holds "last updated", failures and the missed-attendance alert.

## External Services and Dependencies

**Supabase REST.**
- Calls: `POST/GET/PATCH {SUPABASE_URL}/rest/v1/<table>` with headers `apikey` and `Authorization: Bearer <service key>`, server side only.
- Cost: free tier, no card.

**Gemini.**
- Call: `POST https://generativelanguage.googleapis.com/v1beta/models/<model>:generateContent?key=…` with `generationConfig.responseMimeType: application/json` and a `responseSchema`.
- Cost: free tier. On the free tier, Google may use inputs to improve its products, which is why text is scrubbed first.
- The per-day request limit is to be verified. Conversations are batched to stay inside it.

**Meta Graph API (live mode).**
- Calls: `GET /{page-id}/conversations?fields=messages{message,from,created_time}`, `GET /{post-id}/comments`, `GET /{post-id}?fields=reactions.summary(true)`, and `GET /act_{id}/insights`.
- Needs a Meta developer app in development mode and a page access token from the page admin (the learner's one-time, roughly 15-minute step).

**Vercel.** Hosting, Functions and one daily Cron, all on the free Hobby plan.

## Important Failure Modes
- **Gemini quota hit or an error** → that conversation is stored as "not analysed yet" and retried on the next run. The funnel still shows counts.
- **Page / Meta unreachable (live mode)** → the run is recorded as failed, the owner sees the banner, and yesterday's data stays visible (`prd.md > States and Boundaries`).
- **Attendance never ticked** → there is an owner alert, and that day's attended stage shows as "incomplete" rather than 0.

## What Was Simplified and Why
- **Practice-mode data for the demo** instead of the live page. This protects patient privacy and avoids waiting on Meta permissions. Live mode is coded; turning it on takes the learner's page token.
- **One daily cron.** The Hobby plan allows daily crons, so there is no hourly updating. The fuller version would add a paid plan or an external scheduler.
- **The alert is shown in the app**, not sent by email or WhatsApp; notifications are deferred in the PRD.
- **Encrypted real names use a simple server-side key.** A production version would use Supabase Vault or row-level policies.
